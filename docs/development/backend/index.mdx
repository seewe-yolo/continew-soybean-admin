ContiNew Admin 后端基于 Spring Boot 3.5.16（Java 17），脚手架能力由 ContiNew Starter 2.17.0 供给。二次开发前先确认 [项目结构](./structure.mdx) 中的模块划分，再按本组专题页对照落地。

## 通用约定

以下三条约定贯穿全部业务代码，新增功能时先对齐这三条再动手。

### 分层子包

`continew-system` 的 `auth`、`system` 与 `continew-plugin` 下各插件按同一套分层子包组织：`controller`、`service`（含 `impl`）、`mapper`、`model.entity` / `model.query` / `model.req` / `model.resp`，按需补充 `enums`、`constant`、`util`、`config`、`validation`。实体继承 common 的 `BaseDO`（自带 `id`、`createUser`、`createTime`、`updateUser`、`updateTime`、`deleted` 字段），字段由 `MyBatisPlusMetaObjectHandler` 在插入与更新时自动填充。完整分层对照表见 [项目结构](./structure.mdx)。

### 内部 API 解耦

跨模块调用不直接依赖对方 Service。被调方在 `continew-common` 的 `top.continew.admin.common.api` 包定义接口（如 `UserApi`、`TenantApi`），业务模块在自己的 `api/` 子包提供实现并注册为 Spring Bean，调用方只注入接口。模块依赖保持 server → system → common 单向，不会出现循环依赖。`continew-plugin-tenant` 的 `TenantApiImpl`、`continew-system` 的 `UserApiImpl` 都是这一模式的实例。

阿里云 OCR 也遵循同一模式：其他模块注入 `OcrApi` 即可调用身份证、营业执照和发票识别，无需通过 Feign 发起进程内 HTTP 请求。

微信支付 V3 也遵循同一模式：其他模块注入 `WechatPayApi` 即可调用小程序或 JSAPI 下单、订单查询、关单和通知验签解密。实现位于 `continew-plugin-wechat-pay`，公共接口和 DTO 位于 `continew-common`。

支付插件使用普通商户公钥模式，配置来自 `sys_option` 的 `THIRD_PARTY` 类别，默认关闭。商户密钥、公钥和公钥 ID 在三方能力配置页面维护。订单 AppID 必须与配置一致，商户订单号由业务方生成并保证唯一；金额以分为单位，由服务端根据业务订单计算。

业务模块负责提供外网 HTTPS 通知入口，原样传入请求体与四个 `Wechatpay-*` 签名头。`parseNotification` 校验五分钟时间窗口、签名、商户号与 AppID 后返回解密结果；业务模块仍须校验订单归属、币种、金额和支付成功状态，在事务中幂等更新业务订单，并按微信协议返回未被全局响应包装的成功应答。不得只依赖客户端支付成功回调记账。插件未新增无业务归属的公共下单或通知 Controller。

调整支付配置前应等待旧订单处理完成；换商户或换 API v3 密钥会影响旧订单通知。可先关闭支付，再恢复原配置。当前不包含服务商模式、退款、分账与业务订单持久化。

### 全局响应

Controller 直接返回业务对象，Graceful Response（5.0.5-boot3）在出口统一包装为 `top.continew.starter.web.model.R`，字段为 `code`、`data`、`msg`、`success`、`timestamp`。成功码 `0`、失败码 `1`、错误时 HTTP 状态码仍为 200，这些默认值由 `application.yml` 的 `continew-starter.web.response` 配置块固定。导出文件等需要绕过包装的场景，在方法上加 `@ExcludeFromGracefulResponse`（`AbstractCrudController` 的 `export` 方法即如此）。前端约定见 [请求封装](/docs/admin/development/frontend/request)。
